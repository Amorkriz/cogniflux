# ADR-007 仓库与演进：单仓库 + monorepo 触发条件

- 状态：已采纳（2026-07）
- 相关：基线 §2/§4/§5、docs/ARCHITECTURE.md §6

## 背景

只有一个前端应用，但未来可能出现 Agent BFF（第二个应用）与共享包（schema/tokens/ui）。现在就 monorepo 还是单仓库？

## 决策

**单一前端仓库 + pnpm，不做 monorepo。** 用 `src/domains` 域边界与 import alias（`@/* → src/*`、`@content/* → content/*`）保证未来可拆；不预建 `apps/`、`packages/`、`server/` 空目录。

## 理由

- 单应用阶段 monorepo 纯开销（workspace 配置、构建编排、版本联动）。
- 可拆性由纪律保证而非目录结构：域边界 + alias 相对包根解析，意味着"迁移 = 移动目录"，半天级操作。
- 预建空目录违反"抽象按触发条件创建"原则，90% 会成为负债。

## 后果

迁移步骤已文档化（届时执行，每步可独立回滚）：

1. 创建 `pnpm-workspace.yaml`，新建 `apps/web/`，整体 git mv `src/ public/ content/ vite.config.ts` 等（一次提交）。
2. alias 不变，页面代码零修改。
3. 出现第二个消费方时把 `src/domains/*/schema.ts` 抽到 `packages/content-schema`，原位置 re-export 保持兼容。
4. Agent 后端以 `apps/agent-api` 新增，前端只把 `AgentGateway` 从 mock 换成 fetch 实现。

回滚：每步是独立提交，`git revert` 即可；alias 不变保证任意中间态可构建。

## 重新评估条件

- **拆包/monorepo 化触发条件：出现第二个应用**（最可能是 agent-api，阶段 3）。
- `packages/ui` 只在出现第二个 UI 消费方时拆；`packages/design-tokens` 随 agent-api 需要邮件/报告类输出时再评估。
- 触发条件不满足时，任何"顺手 monorepo 化"的提议默认否决。
