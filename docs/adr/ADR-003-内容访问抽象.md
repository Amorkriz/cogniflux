# ADR-003 内容访问抽象：领域 Repository + 适配器

- 状态：已采纳（2026-07）
- 相关：基线 §3/§6/§7、[ADR-002](./ADR-002-内容架构.md)

## 背景

阶段 1 内容来自本地文件，阶段 3 可能来自 CMS/API。若页面直接 import 内容文件，未来切换数据源等于重写页面层。

## 决策

每个领域（`src/domains/x/`）定义仓库接口并提供本地适配器实现（如 `getArticles(options)`、`getArticleBySlug(slug)`），签名统一 **Promise 返回**（按"未来最可能的形态"设计）。领域对外只经 `index.ts` 导出。`src/content-io/`（loader/mdx/validate）是唯一触碰内容文件的层，**只服务 repository**。

**抽象边界**：只做这一层，不做通用 DI 容器/工厂——抽象的收益必须由已知的切换场景（CMS/API）背书。

## 理由

- 一次抽象换取数据源零页面改动切换：CMS 数据进入系统的唯一通道是新的适配器实现，适配器内部把 CMS 结构转为领域类型，页面永不感知 CMS 字段名。
- 反向关联（"谁引用了我"）由 repository 层构建期扫描生成（`getXxxReferenceRecords()` + `src/domains/site/references.ts` 聚合），作者无需双向维护。
- DI 容器对单实现、单消费方的场景是纯负债。

## 后果

- ESLint `no-restricted-imports` 强制：pages/领域组件禁止 import `content/**`；shared 禁止依赖 domains/pages。
- 同步返回的数据也包一层 `Promise.resolve`——为未来异步数据源预留，换实现不改调用方。
- 例外记录：prerender 路径枚举（`scripts/content-urls.ts`）不走 repository（node 环境无 alias 的技术限制），但遵循同一套过滤规则。

## 重新评估条件

出现第二个数据源（CMS/API）时新增适配器实现；出现第二个消费方（agent-api）时把 schema 抽到 `packages/content-schema`（见 ADR-007）。
